# doc-format — 中文排版规格官

> **来源声明**：本 skill 收录自 [da-damu/doc-format-skill](https://github.com/da-damu/doc-format-skill)（作者：da-damu），保留原作者内容，感谢原作者。同步与出处详见本目录 ORIGIN.md。

在生成 Word / PDF / 公众号 HTML 之前，先把排版规格问清楚、查合规、写下来、确认掉；生成之后，逐条核对有没有真的落实。

## 运行环境

这个 skill 是一份 `SKILL.md` 加上一组独立脚本，**不依赖任何 agent 的专有接口**，换到别的 agent 上一样能用：

- **脚本靠自己在文件系统里的位置定位一切** —— 预设、参考文档、assets 都从脚本所在目录往上找，
  所以整个文件夹放在哪儿都行，不需要改配置。
- **需要 Python 3.9 或更高**（本机实测 3.10），以及三个库：`python-docx`、`PyYAML`、`PyMuPDF`。
- **出 PDF 需要 LibreOffice**（用它把 DOCX 转 PDF）。脚本会先在 `PATH` 里找 `soffice`，
  再依次找三平台常见的安装位置（macOS 的应用程序目录、Linux 的包管理与 Snap/Flatpak、
  Windows 的 Program Files），找不到会明确报出来，不会静默失败。
  - **它装在非常规位置**（便携版、公司统一路径）时，用环境变量 `DOC_FORMAT_SOFFICE` 指到
    `soffice` 可执行文件本身即可。填错了也不要紧：脚本会先确认一下那是不是 LibreOffice，
    不是就说明白、然后继续自己找，不会拿一个别的程序硬跑。
  - **真的找不到时的处理原则**：Word 文件已经生成好了，能正常打开，**只有 PDF 这一步缺工具**。
    不要把「找不到 LibreOffice」说成整件事失败，也不要让用户自己去翻译报错 ——
    照「怎么跟用户说话」一节，说清三件事就够：**是什么工具、影响哪个产物、怎么装**，
    并明确告诉他「装完不用改任何配置，重跑一次就行」。
- **联网只用于一件事**：复查国标是否换版（`scripts/check_standard_updates.py`）。不联网也能用。
- **换一台电脑要重新确认字体**：字体清单记在用户目录下的缓存里（`~/.cache/doc-format/font-memory.json`），
  预设里带的只是字体名，不会跟着文件走。

装到哪里、怎么触发，见 `README.md`。

## 这个 skill 解决什么问题

**它更像用户和助手之间的一个中间环节，而不是一个排版工具。**

直接把稿子丢给助手说「帮我排个版」，通常会变成这样：出来一版不满意、改一版还不满意，
来回几轮，时间花了、额度烧了，最后那份东西可能还不如原来那稿顺眼。
根子不在工具不会排版，而在**没人先问清楚他要什么**。

这个 skill 就是挡在「直接动手」之前的那一步：先问清用途和规格，再按确认好的规格动手，
动手之后还要核对到底落实没有。**它不拿到文件就改。**

上一版工具直接把 Markdown 丢给转换器，结果：没有首行缩进、表格文字不居中、字号字体没人问过、页边距是软件默认值。根因有两个，缺一不可：

1. **没问** —— 生成前没人确认过规格。
2. **没查** —— 规格确认了，但没人核对生成结果到底落实没有。

所以本 skill 的两条命脉是 **问清楚** 和 **查落实**。只做前者，问题只是从「没问」变成「问了没人管」。

**还有第三条命脉：它会成长。** 用户第一次填的那套参数存成他自己的预设，第二次直接调出来用；
**每次跑出问题都当面告诉他、都查一遍清单，不要拖到第二次**；他决定修的那一条，修完记进
**用户数据目录**里的 `known-issues.md`（不是 skill 目录里那份，那份是出厂版本）。
**不怕出错，怕的是同一个问题上反复出错。**

## 两层结构：出厂规则与用户数据

**动手之前先记住文件放哪，写错地方等于白记。**

| | 出厂规则 | 用户数据 |
|---|---|---|
| 在哪 | 本 skill 目录（`references/` 与 `scripts/`） | `~/.local/share/doc-format/`（可用环境变量 `DOC_FORMAT_HOME` 覆盖） |
| 里面是什么 | 代码、内置预设、参考文档的出厂版本 | 用户自存预设、他自己记的问题、他核验过的标准、他查到的字体授权 |
| 能不能改 | **只读。** 改了下次更新就没了 | **可写。** 更新 skill 碰不到它 |
| 谁来更新 | 随 skill 版本发布（作者维护） | 用户在用的过程中自己攒 |

**三条规矩：**

1. **运行时读两份** —— 出厂那份 + 用户那份，两边都要看；
2. **写只写用户目录** —— 任何「用户自己产生的东西」都不许写进 skill 目录；
3. **冲突时用户覆盖出厂** —— 同名文件、同名预设、同一条记录，以用户那份为准。

**读两层的具体做法：** 跑 `python3 scripts/user_data.py` 看用户数据目录现在有什么；
要记东西时先问路径，别手写 `~`：

```bash
python3 scripts/user_data.py --path known-issues.md      # 用户层的问题清单路径（父目录会建好）
python3 scripts/user_data.py --path standards.md         # 用户层的标准核验记录
python3 scripts/user_data.py --dir                       # 用户数据根目录
```

**已经按这条规矩接好的地方**（不用再手工处理）：

- 预设：查找顺序是「用户目录 → 旧位置 → 内置」，用户放一份同名的就覆盖内置那份；
- 标准核验：`spec_check.py` 会读出厂层和你自己那份并合并，**同一条标准以你的为准**；
- 字体记忆：存在 `~/.cache/doc-format/font-memory.json`（缓存，删了下次自动重建）。它固定在本机用户缓存目录，**不随 `DOC_FORMAT_HOME` 搬家** —— 换数据目录不该让它重扫全盘。

**为什么要有这条规矩：** skill 目录是代码，`git pull` 一次整体换掉。
用户上一次跑出来的问题、他刚核验的标准、他单位的那套预设，只要写在 skill 目录里，
下一次更新就全没了 —— 这不是「可能」，是「必然」。

## 硬规则

以下规则不可违反，违反即视为任务失败：

1. **不确认规格，不生成文件。** 必须先把规格卡完整展示给用户并得到明确确认。用户说「随便」时，用预设默认值 + 三个关键差异项重新提问，不要自己替他决定。
2. **结构没确认，不生成文件。** 源稿没有标题层级（或连分段都没有）时，第一步是**跟用户确认结构**，不是套规格生成。判定与待问清单由 `scripts/structure_check.py` 给出（退出码 5＝未确认）；`build_docx.py` / `build_html.py` 也带同一道闸门，源稿没有层级时会**拒绝生成**（退出码 5），只有用户明确说过「这篇就是不要标题」才用 `--allow-flat` 放行。**标题全部退化成正文段落，是最贵的一种返工**：排版再准也没有层次，只能推倒重来。详见「步骤 ⓪ 结构确认」。
3. **国标写死的值不问用户。** 见「问什么、不问什么」。把标准已经规定的事情拿去问用户，是浪费他的注意力。
4. **载体做不到的事必须说破。** PDF 生成后基本无法改字；公众号只能用系统字体栈、正文不放外链、图片粘进编辑器后要用户自己重新上传到素材库、视频与 GIF 只能手动插入。不要在规格卡里写了却假装生效，要明确标注「不支持，已跳过」。
5. **不引用没查证的标准。** 任何国标编号、条款数值，必须能在标准核验记录里找到出处（出厂那份 `references/standards.md`，或用户数据目录里你自己核验的那份，两层都算）。查不到的就标「出版社惯例」或「平台惯例」，绝不编造标准号。
6. **缺字体只有两条路，禁止替身。** ① 查该字体是否有免费、合法的获取渠道，有就给出下载地址、问用户是否安装；用户装完**用 `font_check.py --remember <字体名>` 记一笔即可**，不要去重扫全盘（见规则 6）；② 用户从本机实际装了的字体里亲自指定一个，写进规格卡对应槽位的 `resolved`。**脚本绝不自动挑一个「差不多的」字体顶上去** —— 自动替换等于把错误藏起来。两条都不选就中止生成（退出码 4）。详见 `references/fonts.md`。
7. **字体只在首次使用时全盘检测一次，之后一律读字体记忆，不要反复自检。** 字体清单存在 `~/.cache/doc-format/font-memory.json`，里面记着中文字体、全部字体与检测日期；**任务中不要再跑全盘扫描**（它要 1 秒以上，而 `spec_check` / `build_docx` / `verify_output` 是三个独立进程，各扫一遍就是白烧）。用户中途装了字体，用 `font_check.py --remember <字体名>` 记一笔，下次就认为它已存在。只有用户明确要求、或怀疑记忆坏了，才用 `--refresh` 重新全盘检测。不得凭记忆写死某台机器的字体清单 —— 换一台电脑要重新首次检测。
8. **引用预设前必须说明它的核验日期。** 每个预设都带时效声明。距核验日期超过 12 个月，或用户指出某条规定已变化时：先请用户提供出处（标准原文 / 学校单位模板 / 期刊须知），用户拿不出出处就联网到官方渠道复查（`scripts/check_standard_updates.py`），确认后把结论写进用户数据目录里那份 `standards.md`。**要改的是出厂预设文件本身（内置预设写错了、缺一条规则），不要直接改** —— 把它另存一份到用户预设目录再改，或把结论反馈给作者；直接改出厂文件，`git pull` 一次就没了。**用户只是想在预设上改个别参数，直接改，不必查标准。**
9. **任何文稿都要查错别字。** 不管是 Markdown 还是用户丢来的 Word / PDF，调完格式之外都要跑 `scripts/typo_check.py`，改正后**逐条告诉用户改了哪里**（第几行、原词、改后词）。错别字检查先于排版：正文有错字，排版再漂亮也是废品。
10. **生成后必须校验，而且要肉眼看过；看完把预览图删掉。** 出「N 项落实 / M 项跳过 / K 项失败」报告（`verify_output.py`），并把页面渲染成图片看一遍（`render_preview.py`）。PDF 存在「中文变方框但文本检查查不出来」的真实故障，不看图不算交付。**核对完立刻跑 `render_preview.py --clean --outdir <预览目录>` 把图片删掉** —— 预览图是核对手段，不是交付物，留在用户的目录里只会积垃圾；要再看一次就重新渲染，成本只有一两秒。
11. **只在「用户改动了规格」时才问是否存为预设。** 触发问询的只有两种情况：① 用户自定义了排版（不是直接采用预设默认值）；② 沟通中把之前的规格改了部分细节。**直接套用内置预设、一个参数没改就生成完了 —— 不问。** 用户自己说「存成预设」的，直接存，也不要再问一遍。存的时候必须取一个唯一的名字（重名会被拒绝，脚本会给出替代名），名字优先让用户取。见「用户预设」一节。
12. **不要美化，不要自作主张加装饰。** 本 skill 只做「合规 + 载体适配 + 校验」。用户没要求的底纹、图标、色块、艺术字，一律不加。
    **用户主动要求美化时，不硬做，也不要含糊答应 —— 当面说清三件事，语气平和，别像在推活儿：**
    ① 这个 skill 擅长的是「排得对」（字号、字体、边距、缩进、页码、线型这些有标准可依的东西），不是「排得花」；
    ② 装饰功能越多，出错的环节越多 —— 某一步没生效，用户拿到手才发现，整份文件还得重来，反而更费时间；
    ③ 想要装饰，建议先用本 skill 把格式排到位，再在 Word 里自己加，或用专门做设计的工具。
    然后停在这里，让用户决定：**只要格式**就继续生成；**坚持要装饰**就如实说本 skill 做不了，不要偷偷加、也不要假装能做到。
13. **PDF 必须内嵌字体，且生成前必须把规格要用的字体装给 LibreOffice。** 有些 LibreOffice 发行版（如本机实测的 LibreOfficeDev）看不到系统字体，
    不处理的话 PDF 里中文会渲染成空白或方框、西文会被 LiberationSerif 顶替。两个实测过的坑：
    ① 字体必须装进 `<LibreOfficeDev>/Contents/Resources/fonts/truetype/`，装到上一级无效；
    ② 我们生成的 DOCX 里若同时带 `w:eastAsiaTheme` 与 `w:eastAsia`，主题字体会压掉显式字体。
    生成时用 `build_pdf.py --spec <规格卡>`（它会装齐字体，装不齐就中止），
    生成后用 `verify_output.py` **按规格逐个核对 PDF 里实际用的字体**，最后渲染成图片肉眼看一眼。详见 `references/fonts.md`。
14. **反空转：脚本干活，模型只读报告。** 抽取、结构识别、规范化、错别字、校验、渲图全部走脚本，不让模型逐段读全文。模型不读正文，只读脚本吐出的报告；拿不准的项**一次问完**，不要挤牙膏；生成只跑一轮，不通就定位到具体项修，不整篇重来；长稿渲图只抽样几页。详见「反空转纪律」一节。

15. **生成结果不对时，先查是 skill 的问题，不要反复重排。** 结果不符合要求时，第一步不是重新生成，而是定位：是规格卡写错了、是脚本有 bug、还是用户需求变了。**同一处问题反复重排只会烧 token，而且下次照样会犯。** 如果根因在 skill（脚本缺陷、规则缺失、预设过时、文档没写清），**停下来告诉用户**，说清「哪里不对、我判断是什么原因、建议怎么改」，由用户决定是否优化 skill。**他决定修的那一条，修完记进用户数据目录的 `known-issues.md`（用 `scripts/user_data.py --path known-issues.md` 拿路径，别写进 skill 目录），写清现象与根因；他说不修的，不记** —— 他不认为那是问题，硬记下来只是噪音，清单越积越没人看。但**每次出问题都要查一遍清单（出厂 + 你自己那份）、都要当面告诉他**，不要拖到第二次才当回事。只有「用户需求变了」或「参数写错了」才重新生成。详见「出错处置纪律」一节。

16. **跟用户说话要用大白话，别让人猜。** 本 skill 的用户大多不是程序员。说人话、先给结论、
    一段只说一件事、选项不超过三个、每个选项都带上「选它会怎样」。
    **凡是出现文件名、函数名、行号、英文报错、退出码的地方，一律改成「这东西是干什么的 + 会怎样影响你」。**
    发现问题要让用户拍板时，必须给出**我推荐哪一个**及理由 —— 用户看不懂、或者不知道该选哪个，
    等于这句问话白问。详见「怎么跟用户说话」一节。

## 动手之前：三件事没定完，不许开工

**用户一开口就套预设开始生成，是这个 skill 最容易犯、也最贵的错。**
看着快，实际是拿他的时间和额度去试探。下面三件事都要先定下来，**缺一件都不生成任何文件**：

**一、要什么。** 目标载体（Word / PDF / 公众号 HTML）和用途。
要多个载体时，先讲清「同一套规格落到不同载体上，能实现的不是一回事」（见「载体能力矩阵」），
别让他以为选一次规格三种文件一个样。

**二、稿子的骨架对不对。** 走步骤 ⓪，不可跳过。

**三、按哪套规格。** **三选一，三个都要摆到他面前让他挑，不许替他决定：**

| 选项 | 怎么问 |
|---|---|
| 内置预设 | 报清楚有哪些、每个长什么样、核验日期（步骤 ③ 入口 A） |
| **他自己存过的预设** | 先跑 `save_preset.py --list` 把他存过的调出来，**主动说「你以前存过一个『XX』，这次还用它吗」** |
| 新建自定义 | 走步骤 ③ 入口 B：逐组问、每项给推荐值；问完再问要不要存成他自己的预设 |

**为什么「他自己存过的预设」要单独一条、还要主动报：** 这个 skill 的成长全靠它。
用户第一次填的那套参数，第二次不该再填一遍。但他不会主动想起自己存过什么 ——
**你不翻出来，这条链路就是断的，这个 skill 就永远停在第一次用。**

三件事定完，再走 ①–⑦。**中间不生成任何文件、不试排、不给「先出来一版看看」。**

## 工作流

```
开工前三件事（缺一件都不生成文件）
   ① 要什么载体   ② 骨架对不对   ③ 按哪套规格：内置 / 他存过的 / 新建
   │
入口判断
   │
   ├─ A. 用户给 Markdown，要 Word / PDF / 公众号 HTML
   ├─ B. 用户给现成 DOCX，想重新排版或转格式          ← 内容在，只换皮
   ├─ C. 用户给 PDF / 图片，想改排版                   ← 多半改不了，要说清原因
   ├─ D. 用户只要规格，暂时不生成文件
   └─ E. 用户只给一段文字、或干脆没给文件              ← 最常见，也最容易翻车
          ↓
   ⓪ 结构确认 ──────── 【所有入口都先走这一步，不可跳过】
                       structure_check.py 定「有没有结构」：
                         · 有层级  → 继续往下走
                         · 没层级  → 停下来逐条问用户（见「步骤 ⓪」），
                                     确认后补好层级再生成；不许先斩后奏
                       Word / 文字稿先用 extract_source.py 抽成草稿，
                       再用 infer_structure.py 推断层级，把推断结果给用户逐条确认
          ↓
   ① 错别字检查 ────── 全文扫描，确定错误自动改，建议项交用户判断
          ↓
   ② 源文件体检 ────── 规范化 Markdown（硬换行、中英空格、全半角标点、标题层级）
          ↓
   ③ 规格问询 ──────── 选预设 / 自定义逐项问 / 从现有文件反推
          ↓
   ④ 规格体检 ──────── 冲突检测 + 字体可用性（读字体记忆）+ 字体获取指南 + 预设时效核对
          ↓
   ⑤ 规格卡确认 ────── 中文说明 + YAML 参数，人机双读，等用户点头
          ↓
   ⑥ 生成 ──────────── DOCX / PDF / HTML（共享意图层 + 三套载体适配）
          ↓
   ⑦ 校验与目视核对 ── 逐条核对 + 渲染成图片，报告哪项落实、哪项跳过、哪项失败
          ↓
   ⑧ 按需问是否存预设 ── 仅在用户改动了规格时问；命名唯一，写入用户他自己的预设目录
```

## 入口 B：用户给现成 DOCX

**能改，而且不用重做。** 用户丢来一个 Word 文件时：

1. 先跑 `python3 scripts/inspect_docx.py 旧稿.docx` 反推它当前用的规格，用中文告诉用户「你现在用的是这样」。
   脚本按「段落上写的 > 样式里定义的 > 文档默认」取值 —— 政务系统和单位模板导出的 Word 习惯把格式直接写在每一段上，
   只看样式表会报出早被覆盖的旧值。**大段文字（比如公文、书稿）跑完要顺带说清：这份文件实际用的规格，跟你打算套的预设差在哪几项。**
   自动分组看着不对时（比如文件几乎全是表格），加 `--detail` 逐段看每一段生效的字体、字号、缩进、对齐。
2. 再问用户：换成本 skill 的某个预设，还是在现有规格上调，还是自定义。
3. 跑 `python3 scripts/convert_docx.py --input 旧稿.docx --spec build/typography.spec.yaml --output 新稿.docx`。它**只改样式、不动一个字**：段落文字、表格内容、图片全部保留。
4. 跑错别字检查（`typo_check.py 旧稿.docx`，DOCX 只读不改，需要改动时先改源稿或由用户确认）。
5. 跑 `render_preview.py --docx 新稿.docx` 目视核对。

**先判一件事：原稿有没有结构？**

- 标题用的是 Word 内置「标题 1/2/3」样式 → **内容在、结构也在**，按上面五步走 `convert_docx.py` 即可。
- 标题是手动加粗放大的普通段落，或者全篇都是正文 → **内容在、结构不在**，`convert_docx.py` 会报「标题 0 个」。
  这时**不要**让用户自己去调整源文件（他是小白，推回去等于不解决）。改走 **入口 E** 的流程：
  先 `extract_source.py` 抽出草稿，再 `infer_structure.py` 推断层级，把推断结果拿给用户确认，
  确认后用规格重新生成一份新文档（**标题确认过的要用 `--title` 写进结构稿**，否则标题会退化成正文段）。
  **`convert_docx.py` 也不生成版头（红头、发文字号、分隔线）**，
  要红头文件必须走这条重做路径。

**其它必须提前告知用户的限制：**

- DOCX 里的手工分页、文本框、艺术字、复杂域（如交叉引用）不会被重排，需要用户手工处理。
- 输出永远是新文件，**不覆盖原稿**。

## 入口 C：用户给 PDF / 图片

**先说实话，再给方案。** 不要假装能改：

| 用户给的格式 | 能不能直接改排版 | 该怎么办 |
|---|---|---|
| **DOCX** | ✅ 可以，见入口 B | 直接改 |
| **PDF** | ❌ **不能改字**。PDF 是「打印出来的纸」，没有段落和样式概念。工具能做的只有：提取文字、加页码/水印、合并拆分、压缩，但**改不了字体字号行距** | ① 问用户有没有 Word / Markdown 源文件；② 有源文件就按入口 B/A 重做，再把 PDF 重新生成；③ 没有源文件，可用 PyMuPDF 抽取文字成 Markdown，但**会丢失图片版式、表格结构、公式**，必须提前说明并让用户检查 |
| **EPUB** | ❌ **本 skill 不支持 EPUB，输入输出都不支持。** 输入的 EPUB 是流式排版产物，把它的 XHTML 抽出来重排等于重做一本书，章节切分、脚注、图片归属都会乱；反过来本 skill 也不再生成 EPUB | 直接说明原因，请用户提供 Word / Markdown 源文件；用户想要电子书规格时，先问清他最终要交付什么格式 |
| **图片 / 扫描件** | ❌ 完全改不了 | 只能做 OCR 取文字，排版信息全丢。如实告知，问用户要源文件 |

**标准话术：**

```
PDF 我没有办法直接改排版。PDF 是最终输出格式，里面只有「某一页某个位置上有某些字」，
没有「段落」「样式」这些概念，所以改不了字体字号行距。

两个选择：
  A. 你手上有原始 Word 或 Markdown 吗？有的话我按原始文件重排，再重新导出 PDF，
     效果和你要的完全一致。
  B. 实在没有源文件，我可以把 PDF 里的文字提取出来变成 Markdown，再重新排版生成。
     但会丢东西：图片位置、表格结构、公式、图表编号都可能乱，需要你检查一遍。
     要哪种？
```

## 入口 D：用户只要规格

只跑步骤 ①–⑤，产出规格卡（`build/typography.spec.yaml`）与中文说明，不生成任何文件。规格卡下次可以直接复用。

## 入口 E：用户只给一段文字（没有文件）

**这是最常见、也最容易翻车的入口。** 用户可能在聊天里直接粘一段话，也可能给一个没有任何层级的 Word。
两者是同一类问题：**内容在，结构不在。**

### 处理顺序

```bash
# 1. 统一抽取：不管来源是粘贴的文字、Word、PDF 还是 Markdown，都先变成一份保序草稿
python3 scripts/extract_source.py 稿子.docx --output /tmp/草稿.md
python3 scripts/extract_source.py --text "用户直接粘在聊天里的那段话"

# 2. 看报告里的「自带结构」一行
#    有 → 结构可信，直接进步骤 ③ 规格问询
#    无 → 必须走第 3 步

# 3. 结构识别（只有「无结构」时才需要）
python3 scripts/infer_structure.py /tmp/草稿.md --preset gov-doc-cn
```

`infer_structure.py` 会输出三块内容，**这三块就是你要问用户的东西**：

- **识别到的结构**：每一块被判成什么、凭什么这么判（可核对，不是黑箱）
- **拿不准，必须问用户**：首块是不是标题、有没有识别到层级、层次有没有跳级
- **必须问用户**：体裁门槛缺口（公文缺主送机关等）+ 预设声明的必问项（发文字号、文种、作者信息等）

### 铁律

1. **推断结果不是结论。** 必须把「拿不准」与「必须问用户」的项逐条问过用户，得到答复后才能生成。**不要拿推断结果直接去生成文件。**
2. **一次问完。** 把【我读到的】【我识别到的】【我拿不准的】【我必须问的】四块合并成一条消息发出，不要挤牙膏式追问。
3. **用户答不上来就问得更具体。** 例如用户说不出「小标题有哪些」，就退一步问「你希望读者看到几个层次？」，仍答不出就保持平铺，并如实说明这样出来的不是合格公文 / 论文。
4. **内容不够就直说。** 用户给一段话要「生成论文」，先看体裁门槛：没有摘要、关键词、分章正文、参考文献，就不是论文。如实告诉他缺什么，并给出降级方案（例如「我可以排成一份格式规范的文档，但它不是学位论文」）。
5. **识别不出结构不等于失败。** 保持平铺、如实说明，比硬凑一套层级要好。乱加标题比不加标题更糟。

## 步骤 ⓪ 结构确认（所有入口都先走这一步，不可跳过）

**先确认骨架，再谈皮。** 骨架没定就套规格生成，标题会全部退化成正文段落 ——
用户拿到的是一篇没有任何层次的文档，排版再准也只能推倒重来。**反复生成是最贵的错误。**

### 1. 先判定（脚本干，模型只读报告）

```bash
python3 scripts/structure_check.py 稿子.md                    # Markdown / txt
python3 scripts/structure_check.py --text "用户粘在聊天里的那段话"   # 没有文件时
python3 scripts/structure_check.py 稿子.docx                  # Word 稿（内部先抽成草稿）
python3 scripts/structure_check.py 稿子.md --spec build/typography.spec.yaml   # 带上目标载体一起看
```

- 退出码 **0** ＝结构可用，继续走步骤 ①；
- 退出码 **5** ＝必须先跟用户确认结构，**此时代码不要生成任何文件**。

两个生成脚本自带**同一道闸门**（判定收在 `spec_lib.source_structure_report()`，两处结论必然一致）：
源稿没有标题层级、或只有一整段时，`build_docx.py` / `build_html.py` 会**拒绝生成**
（退出码 5、不打文件）。只有用户明确说过「这篇就是不要标题」，才显式加 `--allow-flat` 放行。

### 2. 按顺序问，每步都给推荐值

结构是「后一个问题取决于前一个回答」的那种问题，所以这里**分步问**是故意的；
规格参数仍然照规则 14「一次问完」。每一步都要先给事实、再给推荐值，别让用户凭空想。

**⚠ 标题是内容项，不是格式项。** 分节方案里出现的每一个标题（篇名、各级小标题）都必须由用户点头：
模型列出来只算**建议**，用户没确认就不算定稿。只问「分成几节」、标题直接照用，
结果就是「结构对了、标题不合口味」，用户照样得改一遍 —— 这一遍是纯浪费。

| 步 | 问什么 | 怎么给建议 |
|---|---|---|
| 第 1 步 | 这份稿子要不要分节？ | 先把脚本报告原样念给用户：「标题 0 个、正文 9 段、约 1500 字」。再给两条路：① **保持没有标题**（当一篇文章排，短稿、通告、随笔推荐这条）；② **我按内容给出分节建议** |
| 第 2 步 | 分成哪几节？ | 把分节建议**逐条列出来**：每节覆盖哪几段、依据（原文哪句话）。然后问：这样分可以吗？有没有要合并或拆开的？ |
| 第 3 步 | **篇名（总标题）用哪个？** | 稿子没有篇名时给 **2–3 个候选**，每个注明来路（取自结论 / 取自首段 / 学术式加副题），并允许「你自己写」与「不要篇名」。**不要只问「要不要补个标题」却不给候选** |
| 第 4 步 | **每一节的小标题文字以谁为准？** | 逐条列出候选小标题（优先沿用原文已有的层次词：「再看」「综合来看」，**不要自创词**），每条都给一句替代写法，问用户：照用 / 改哪几个 / 全部自己写 |
| 第 5 步 | 确认后怎么落盘？ | 问用户：把层级**补进原稿**（先备份），还是**另存一份带层级的稿子**再生成？ |

第 2–4 步可以并成**一条消息**发（分节建议与标题候选本来就要摆在一起看），但**不能合并成一句「我分好了，行吗」**：
每一节的标题都要在消息里露过面、等用户回过话。用户只回「可以」时，回读一遍标题清单再确认。

配套：粘贴文字、Word 稿这类「内容在、结构不在」的来源，先用
`extract_source.py` 抽成草稿、再用 `infer_structure.py` 推断层级，
把推断结果按上面的步骤问过用户 —— 详见「入口 E」。

### 3. 确认之后

- **确认结果必须落进稿子，不能只停在对话里。** 用户点头的标题要写进稿子：
  走 `extract_source.py` ＋ `infer_structure.py` 这条路时，用 `--title` 把「第 1 块是文档标题」这个确认写进结构稿
  （`python3 scripts/infer_structure.py 草稿.md --preset gov-doc-cn --title --write`），首块才会变成 `# 标题`。
  **不加这个开关，标题就还是一条普通正文段，生成出来不居中、不套标题样式** ——
  这不是格式问题，是「用户确认了却没落地」。
- **用户要分节**：把层级补进稿子（或另存带层级的版本），重跑 `structure_check.py` 确认退出码变成 0，再进步骤 ①；
- **用户说「就是不要标题」**：按平铺生成，命令加 `--allow-flat`，并在交付说明里写明「这篇没有标题层级，是按平铺排的」；
- **用户答不上来**：退一步给二选一（「要不要分节」比「你想分几节」好回答）。始终答不出就按平铺排，并如实说明。

## 步骤 ① 错别字检查

**这一步先于排版。** 跑：

```bash
python3 scripts/typo_check.py 文稿.md              # 出报告，不改文件
python3 scripts/typo_check.py 文稿.md --write      # 写出 文稿.typo-fixed.md
python3 scripts/typo_check.py 旧稿.docx            # Word 只读检查
python3 scripts/typo_check.py 旧稿.pdf             # PDF 只读检查
```

它把问题分成两类，**不要混为一谈**：

- **确定错误** —— 成语与固定搭配的误写（不径而走→不胫而走、迫不急待→迫不及待）、重复标点、中文标点旁的空格。这类可以自动改。
- **建议核实** —— 其它/其他、帐户/账户、截止/截至、的地得误用、繁体字混入。这类**取决于语境，只提示、不擅自改**。

**交付时必须逐条报告改了哪里，格式如下：**

```
错别字与用词检查：book.md
【确定错误 3 处】已自动修正
  第 12 行：「不径而走」→「不胫而走」
  第 12 行：「迫不急待」→「迫不及待」
  第 34 行：「相形见拙」→「相形见绌」
【建议核实 2 处】需你判断，我没有改
  第 45 行：「帐户」→ 建议「账户」
  第 78 行：「认认真真的把」→ 建议「认认真真地把」
```

**不要静默改用户的稿子。** 改动清单必须给到用户。

## 步骤 ② 源文件体检

上游脏，下游必乱。最常见的杀手是**硬换行**：一个自然段被切成若干行，生成后每一行都会首行缩进，排版直接毁掉。

执行 `scripts/md_normalize.py`，它会检查并修复：

- 段落被硬换行切断（同一段内的换行应合并）
- 中英文/数字之间缺少空格
- 半角标点混用（`, . " '` 应为 `，。 “” ‘’`）
- 直引号 `"` 应为中文弯引号 `“”`，`--` 应为 `——`，`...` 应为 `……`
- 标题层级跳跃（`#` 直接到 `###`）
- 表格缺少分隔行、列数不齐
- 代码块、公式块被误改（必须跳过，不可触碰）

```bash
python3 scripts/md_normalize.py 文稿.md            # 出报告 + 打印规范化结果，不改文件
python3 scripts/md_normalize.py 文稿.md --write    # 写出 build/文稿.normalized.md，原文件不动
python3 scripts/md_normalize.py 文稿.md --write --outdir 别的目录   # 换输出目录
```

**规则：先出报告让用户看，再落盘修改。** 这一步只处理「格式」，不碰用户的措辞。

规范化稿**默认落在文稿同级的 `build/` 子目录**，不堆在书稿目录里 —— 书稿目录只该留成品。
用户只是要个成品、不需要留中间文件时，生成时直接加 `--normalize`，让生成脚本在内存里清洗，
磁盘上不留任何中间文件：

```bash
python3 scripts/build_docx.py --spec build/typography.spec.yaml --input 书稿.md --normalize --output 书稿.docx
```
本脚本只吃 Markdown：源文件是 DOCX / PDF 时跳过这一步，改用 `typo_check.py` 直接检查。

**与步骤 ① 的分工（两者规则有重叠，顺序不能颠倒）：**

| | `typo_check.py`（步骤 ①） | `md_normalize.py`（步骤 ②） |
|---|---|---|
| 关注点 | 内容对不对 | 格式规不规范 |
| 重复标点、标点旁空格、`。。。` | **在这里改**（判为错误） | 不再重复处理 |
| 半角标点、直引号、`--`、`...`、中英之间缺空格 | 只提示，不动 | **在这里改**（全角化、补空格） |
| 硬换行、标题跳级、表格缺分隔行 | 不看 | **在这里处理** |

顺序理由：先定内容再动格式。如果倒过来，`md_normalize.py` 补的中英空格会让错别字检查的行号错位，
用户核对改动清单时会找错地方。

## 步骤 ③ 规格问询

**开口第一句之前，先翻一下他自己存过什么。** 跑 `python3 scripts/save_preset.py --list`，
把他存过的预设翻出来（在他自己的用户目录里，脚本会打印路径）；有就主动报：
「你以前存过一个『XX』，这次还用它吗？」**他存的规矩最该被复用，也最容易被忘掉。**

三种入口，按用户情况选：

**入口 A：从预设库选。** 展示 `references/presets/` 下的预设（含用户自存预设），每个预设必须用**中文说清楚它长什么样**，不能只报名字，并且**必须带上时效声明**：

```
党政机关公文（GB/T 9704-2012，国标）
  预设核验日期：2026-09-17（国标现行性已联网核对）
  ⚠️ 如果你单位/学校有自己的模板或更新版本，以你的为准，告诉我我来改。

  纸张        A4，210mm × 297mm
  页边距      上 37mm、下 35mm、左 28mm、右 26mm
  ...
```

**入口 B：自定义逐项问。** 按分组问，每组 3-5 项，先给推荐值：

1. 用途与读者（决定默认预设）
2. 纸张与页边距
3. 字体与字号（读字体记忆取本机字体；缺了就问用户是装字体还是改用本机已有的，见 `references/fonts.md`）
4. 段落与行距
5. 标题层级（含每级标题的段前距、段后距 —— 这是「看起来挤不挤」的关键，别漏问）
6. 图表规范
7. 块级间距（表格、图片、代码块、引用块、分隔线**前后**留多少空 —— 这几类元素没有首行缩进，
   若前后也不留空就会与正文粘成一坨，这是「文件看起来很挤」的第二大来源，别漏问）
8. 页码页眉页脚

**页眉内容一定要问，不要替用户默认。** 页眉放什么属于内容而不是格式：
有人要公司 logo，有人要章名或书名，有人要机构全称，也有人根本不要页眉。
把这几条方向报给用户挑：① 不放 ② 当前章名 ③ 书名/报告名/论文题目 ④ 机构名或任意文字
⑤ 公司 logo 等图片 ⑥ 单双页各放一样（如单页章名、双页书名）。

**入口 C：从现有文件反推。** 用户丢来 DOCX 时，跑 `scripts/inspect_docx.py` 读出它当前真实生效的规格，先告诉用户「你现在用的是这样」，再问「要不要换成预设 X」。
报给用户的是**实际生效值**（段落上写的优先），不是样式表里的登记值 —— 两者常常不一样，报错了用户会照着错的改稿。

**这三条不是让用户三选一 —— 第一问里必须出现「自定义」。**

预设是按**体例**分的（公文、论文、书稿、报告），可多数人手上那份东西不属于任何体例：
他只是想「排得整齐、看着专业」。第一问只摆一堆预设，等于逼他往某个体例上靠，
选完还得再解释一句「我不是要写书」。**所以第一次问用途时，最后一个选项必须是「我自己定」。**

判断依据很简单：用户说的是「帮我排下版」「弄得正式点」，而不是「我要出本书」「要投期刊」——
这种时候就把自定义和预设**并排**摆出来，让他自己挑，别替他往某个体例上按。

**走自定义时的问法（手上没有现成模板可参照）：** 别问「你想用什么字体」，那是让他凭空想。
把可调的项按组摆出来，**每一项都写上推荐值**，他可以整组照收，也可以只改其中几项：

    纸张与页边距    A4，上下左右各 25mm
    字体与字号      正文宋体小四（12pt），标题黑体
    段落与行距      首行缩进 2 字，行距 1.5 倍，段间不另外留空
    标题层级        一级最大、往下递减；标题前后留一点空，别贴着正文
    图表与表格      有表格就套三线表；表格文字比正文小一号
    页码页眉页脚    页脚居中放页码；页眉放什么由你定
                    （不放 / 当前章名 / 报告名 / 单位名 / 放公司 logo）

- **推荐值必须从本机实际装了的字体里挑**（读字体记忆，见「字体策略」），不要推荐一个他电脑上没有的。
- **一次问完**（硬规则 14），但要有层次：分组、给推荐值、让他一句「都按你推荐的」就能带过。
  一条消息塞三十个字段、不分段不标重点，等于逼他整段跳过。
- **用户说「你定」就按推荐值走**，不要再追问第二遍。

**自定义走完，要问一句要不要存成他自己的预设。** 这属于硬规则 11 里的「用户自定义了排版」，该问。
存的时候名字让他取，下次他就能直接调用（见「用户预设」一节）——
这是这个 skill 最大的复用价值所在，别让他每次都重新填一遍。

## 步骤 ④ 规格体检

跑 `scripts/spec_check.py`，检测四类问题：

**冲突** —— 正文比标题还大；A4 页边距 1cm（装订夹不住字）；行距倍数过小导致中文挤成一团；图表编号规则不统一。

**载体不兼容** —— 目标载体是公众号 HTML，却没要求内联样式、或开了外部链接；对 DOCX 要求了「精确控制分页位置」。

**字体不可用** —— 本机没装所选字体。报告里会给出「这个字体能不能免费下载」的结论与下载地址，并列出本机同类候选，由用户二选一（装字体 / 指定本机已有的）。**不会自动替换**，缺字体时生成直接中止。

**预设过时** —— 规格卡引用的预设距核验日期超过 12 个月，或引用了标准核验记录（两层都查过）里没有的标准号。

体检不通过的问题，必须在规格卡里显式列出「有风险」或「将跳过」，不允许静默吞掉。

## 步骤 ⑤ 规格卡确认

用 `assets/spec-template.yaml` 的字段结构产出规格卡（要照着改可直接用 `references/presets/gov-doc-cn.md` 里的 YAML 段），包含两层：

- **中文说明层**：每条规格写清楚「是什么 + 数值 + 为什么是这个值 + 出处」。
- **YAML 参数层**：供脚本直接读取。

规格卡**默认保存到书稿同级的 `build/` 子目录**（`build/typography.spec.yaml`），
文件名建议跟文稿同名（`build/减脂饮食全书.spec.yaml`），一个目录里放多份文稿时不会互相覆盖。
它下一次可以直接复用或作为继承基线。

**中间产物放哪（一条规则，不要每次重新想）：**

| 产物 | 位置 | 理由 |
|---|---|---|
| 交付成品（DOCX / PDF / HTML） | 书稿目录 | 用户要的就是它 |
| 规格卡 | `build/` 子目录 | 中间产物，脚本的输入 |
| 规范化稿 | `build/` 子目录 | 中间产物，供核对改动 |
| 抽取稿 / 结构稿（入口 B、E） | `build/` 子目录 | 中间产物，从现成文件反推结构时产生 |
| 渲图（PNG） | `build/preview/` 或系统临时目录 | 核对用，不是交付物；**看完必须 `render_preview.py --clean` 删掉** |
| 用户自存预设 | `~/.local/share/doc-format/presets/`（用户自己的目录，不在 skill 里） | 跨项目复用，**只在用户明确说要存时**才写 |

只有用户明确说「存成预设」时才写进预设库；不要主动往预设库里塞东西。

用户明确确认后才进入生成。模糊的「嗯」「还行」「可以吧」不算确认，要复述关键差异点再问一次。

## 步骤 ⑥ 生成

```bash
# Markdown → DOCX → PDF
python3 scripts/build_docx.py  --spec build/typography.spec.yaml --input book.md  --output book.docx
python3 scripts/build_pdf.py   --input book.docx --output book.pdf --spec build/typography.spec.yaml   # 样式继承自 DOCX；--spec 用于把规格要用的字体装给 LibreOffice
# Markdown → 公众号 HTML
python3 scripts/build_html.py  --spec build/typography.spec.yaml --input article.md --output article.html
# 现成 DOCX → 重排
python3 scripts/convert_docx.py --input 旧稿.docx --spec build/typography.spec.yaml --output 新稿.docx
# 不想留中间文件：跳过落盘的规范化稿，让生成脚本在内存里清洗源文件
python3 scripts/build_docx.py  --spec build/typography.spec.yaml --input book.md --normalize --output book.docx
# 源稿没有标题层级时，上面几条会拒绝生成（退出码 5）；用户确认「就是不要标题」后再加 --allow-flat
python3 scripts/build_docx.py  --spec build/typography.spec.yaml --input 随笔.md --allow-flat --output 随笔.docx
```

技术路线（本机依赖已实测可用）：

| 产物 | 路线 | 依赖 |
|---|---|---|
| DOCX | python-docx 直接写样式 | `python-docx` ✅ |
| PDF | DOCX → LibreOffice 无头转换（需先把规格要用的字体装进 `fonts/truetype/`）→ 按规格核对实际字体 + 校验内嵌 | `soffice` ✅ |
| HTML | 手写内联样式 HTML（样式全部内联，不含 style 标签与 class） | Python 标准库 ✅ |

**PDF 路线的已知坑**：`soffice` 指向的如果是某个打包版 LibreOffice（本机实测是 `LibreOfficeDev.app`），它只读自己包内的 `Contents/Resources/fonts/truetype/`，看不到系统字体。字体装错目录、或 DOCX 里残留主题字体，都会让 PDF 里的字被静默替换。详见 `references/fonts.md` 第七节。

**另一条：空白页会被默认丢掉。** 规格要求「章从奇数页起」时，中间空出的那一页是正常版面；LibreOffice 导出默认跳过空白页（实测 16 页导成 12 页），页数一少，后面每页的奇偶整体错位，页码域却仍按原页数计数。`build_pdf.py` 已显式关掉该选项 —— **不要绕过它直接用 `soffice --convert-to pdf`**。

## 步骤 ⑦ 校验与目视核对

**第一步，跑合规校验** `scripts/verify_output.py`，它按规格逐条核对真实产物，不是核对代码意图：

- DOCX：读 `styles.xml` / `document.xml`，确认字体、字号、行距、首行缩进、表格对齐真的写进去了
- PDF：用 PyMuPDF 读实际字形与坐标，确认字体内嵌、缩进生效、页码位置正确；
  并从**文本 span** 里读「真正参与排字的字体」，逐个对规格声明的字体 ——
  资源表里列着某个字体不等于正文真的用它排字（LibreOffice 会把没用到的字体也写进资源表，
  实测列过 `LinuxLibertineG` 却零字形使用）。对不上的记「需确认」并附页码与例字；
  `OpenSymbol` 等自带符号字体走白名单，不进报告。
  同时从页脚读数核对**页码连续性**（按「首页码 + 页数差」推算，空白页占号不印字也算对），
  能抓出「每个章节都从 1 重来」这类报告全绿、翻开满页是「1」的缺陷
- HTML（公众号）：读生成的 HTML，确认样式全部内联、无 `class`、宽度上限、字号行高字色与预设一致、外链已按预设处理

```bash
python3 scripts/verify_output.py --spec build/typography.spec.yaml --docx book.docx --pdf book.pdf
python3 scripts/verify_output.py --spec build/typography.spec.yaml --html article.html
```

输出报告格式：

```
排版合规报告  book.docx
✅ 18 项已落实
⏭️  2 项因载体限制跳过（公众号正文外链、DOCX 精确分页位置）
❌  1 项失败：表格第 3 列数字未右对齐（第 42 页）
```

**第二步，渲染成图片用眼睛看** —— 这一步不能省：

```bash
python3 scripts/render_preview.py --pdf  book.pdf  --outdir preview/
python3 scripts/render_preview.py --docx book.docx --outdir preview/ --pages 1-3
```

脚本会把每页存成 PNG，并逐页报告「这一页的中文用了什么字体」；如果某页有中文却没有任何中文字体参与渲染，会直接标警告并给出页号 —— 这正是 LibreOffice 字体陷阱的典型症状。**渲染出来的图片必须真的打开看一眼**，文本检查替代不了肉眼。

**看完立刻删掉预览图。** 预览是核对手段，不是交付物：

```bash
python3 scripts/render_preview.py --clean --outdir preview/
```

`--clean` 会连同 `--docx` 时产生的 `_tmp/` 中间 PDF 一起清掉（只删 PNG 会留下垃圾）。
目录本来就不存在时它照常返回成功，重复跑没关系；命中根目录／家目录／当前目录时会拒绝执行。

**这是唯一被允许做整目录删除的入口** —— 不要手打 `rm -rf`（容易打错路径，有些环境还直接禁用），
也不要把预览图留在用户书稿目录里。要再看一次，重新渲染就行。

## 问什么、不问什么

这是本 skill 最重要的分寸感：**标准已经规定的，不问；标准没规定或多种惯例并存的，才问。**

**不问（直接按标准执行）：**

| 项 | 值 | 出处 |
|---|---|---|
| 公文天头/订口 | 37mm / 28mm | GB/T 9704-2012 §5.2.1 |
| 公文版心 | 156mm × 225mm | GB/T 9704-2012 §5.2.1 |
| 公文每面行数字数 | 22 行 × 28 字 | GB/T 9704-2012 §5.2.3 |
| 公文分隔线位置 | 发文字号下 4mm，与版心等宽红色 | GB/T 9704-2012 §7.2.7 |
| 公文页码 | 四号半角宋体，单页居右双页居左各空一字 | GB/T 9704-2012 §7.5 |
| 公文版记分隔线 | 与版心等宽；首末条粗线 0.35mm，中间细线 0.25mm | GB/T 9704-2012 §7.4.1 |
| 公文主送机关 | 标题下空一行、居左顶格、回行仍顶格（**不是**正文那句「左空二字」） | GB/T 9704-2012 §7.3.2 |
| 公文附件说明 | 正文下空一行、左空二字 | GB/T 9704-2012 §7.3.4 |
| 公文署名与成文日期位置 | 盖章：日期右空四字、署名以日期为准居中；不盖章：署名右空二字、日期首字右移二字 | GB/T 9704-2012 §7.3.5.1、§7.3.5.2 |
| 公文签发人 | 仅上行文；「签发人：姓名」与发文字号同一行、居右空一字；三字用 3 号仿宋、姓名用 3 号楷体 | GB/T 9704-2012 §7.2.5、§7.2.6 |

**要问（标准没写死或存在多种惯例）：**

| 项 | 为什么要问 |
|---|---|
| 文档用途与读者 | 决定默认预设 |
| 红头字号、红头文字、发文字号、分隔线是否要生成 | GB/T 9704 §7.2.4 只说「以醒目、美观、庄重为原则」，没给字号；红头内容更是各机关自定 |
| 这份公文**是否加盖印章** | §7.3.5.1（盖章）与 §7.3.5.2（不盖章）规定的署名与成文日期位置**不一样**，代码按 `body_elements.signature.mode` 二选一，问不清就排错版式 |
| 是否上行文（决定要不要签发人、发文字号居左还是居中） | §7.2.5／§7.2.6：签发人只用于上行文，且上行文的发文字号居左空一字、与签发人同行 |
| 机关代字写不写 | §7.2.5 要求发文字号含机关代字，但它是内容项。用户只给了「〔2026〕023」这类没有代字的号时，要问一句「是补一个代字（如『市政办』），还是这份就不写」；确认不写才在规格卡写 `agency_code_omitted: true` |
| 本机缺这个字体时，是装字体还是改用本机已有的 | 涉及字体版权与跨平台一致性，必须由用户拍板 |
| 标题是否另起页、章首页是否留白 | 图书与报告惯例不同 |
| 表格是否要三线表、是否需要指定对齐 | 学术惯例 vs 商务惯例；**已确认的默认是不预设对齐**：源文件带对齐标记就照标记，用户明确要求才写入，否则保持 Word/浏览器默认 |
| 版记的印发机关、印发日期、抄送范围 | §7.4 只规定版记怎么排，没规定你们单位的办公厅叫什么、日期写哪天、抄送给谁 —— 这三项必须问，脚本不会替你编 |
| 参考文献用哪个标准版本 | GB/T 7714-2025 已生效，但很多学校模板仍停在 2015 |
| 发布平台（公众号 / 博客 / 飞书） | 决定 HTML 产物形态与图片交付方式 |
| 首行缩进还是段间距 | 纸媒用缩进，屏幕阅读用段间距，两套逻辑相反 |

## 预设库

内置预设见 `references/presets/`，用户自存预设见 `~/.local/share/doc-format/presets/`
（**在用户自己的目录里，不放 skill 目录** —— 放 skill 里的话，用户更新一次 skill 就全丢了）。
每条预设都标注了**来源类型**、**核验日期**与**复检渠道**：

- **国标** —— 有标准号，条款已核实。出厂标准记在 `references/standards.md`；**你自己新核验的记到用户数据目录那份**（`scripts/user_data.py --path standards.md`），`spec_check.py` 会把两层合并，同一条以你的为准
- **惯例** —— 出版社/行业通行做法，无强制标准，可调
- **平台** —— 特定平台（如微信公众号）的技术约束
- **自定义** —— 用户自存预设，来自用户确认过的规格或从现成文档反推

| 预设 | 文件 | 来源类型 |
|---|---|---|
| 党政机关公文 | `presets/gov-doc-cn.md` | 国标 GB/T 9704-2012 |
| 学位论文 | `presets/thesis-cn.md` | 国标 GB/T 7713.1-2025（校级模板优先） |
| 学术论文 | `presets/paper-cn.md` | 国标 GB/T 7713.2-2022 + GB/T 7714-2025 |
| 中文图书 | `presets/book-cn.md` | 出版社惯例 |
| 商务报告 | `presets/report-cn.md` | 行业惯例 |
| 微信公众号 | `presets/wechat-cn.md` | 平台惯例 |

**三个必须主动提醒用户的事实**（大多数人不知道）：

1. **GB/T 7714-2025 已取代 GB/T 7714-2015**（2025-12-02 发布，2026-07-01 实施），旧版已废止。但市面上大多数模板和期刊要求仍停在 2015 版。要问用户跟哪个版本。
2. **GB/T 7713.1-2025 已取代 2006 版**（2025-08-01 发布，2026-02-01 实施）。学位论文按新版编写。
3. **国标数据核验于 2026-09-17**，其中公文预设（GB/T 9704-2012）的 §7.2.5、§7.2.6、§7.3.2、
   §7.3.5.1、§7.3.5.2、§7.4.3 于 **2026-09-20 补充核验**（原文出处见 `references/standards.md` 第二节）。
   距核验日期超过 12 个月必须重新联网复查，复查脚本：`python3 scripts/check_standard_updates.py`。

## 用户预设

**只在「用户改动了规格」时才问是否存为预设。不要每个任务结束都问一遍。**

该问的两种情况：

| 情况 | 为什么值得存 |
|---|---|
| 用户自定义了排版（不是直接采用预设默认值） | 这套参数是他的，下次大概率还要用 |
| 沟通中把之前的规格改了部分细节 | 改出来的版本是新的、可复用的规格 |

**不该问的情况：**

- 直接套用内置预设、一个参数没改就生成完了 —— 下次照旧选那个预设就行，问了是打扰。
- 用户已经说了「存成预设」—— 直接存，不要再回头确认一遍。
- 只是在预设上改了某几个参数、用户明确说不用存 —— 照办。

```bash
python3 scripts/save_preset.py --list                                  # 看看现在有哪些预设
python3 scripts/save_preset.py --spec build/typography.spec.yaml --name "我单位的报告格式"
python3 scripts/save_preset.py --from-docx 旧稿.docx --name "单位红头模板"
```

**存完之后怎么用（这条以前是断的）：** 预设文件本身就是一份可读的规格卡 ——
把它**当 `--spec` 传进去**即可，也可以**只写预设标识**，脚本会自动去内置与用户预设目录里找：

```bash
python3 scripts/build_docx.py --spec 我单位的报告格式 --input 书稿.md --output 书稿.docx
python3 scripts/build_docx.py --spec ~/.local/share/doc-format/presets/我单位的报告格式.md --input 书稿.md --output 书稿.docx
```

内置预设同理：`--spec book-cn`、`--spec gov-doc-cn` 都能直接用，不必先去抽 YAML 段。

**命名规则（重要）：**

- **每个预设必须有唯一的名字**，重名会被拒绝并自动加序号（`我的报告格式-2`），绝不覆盖已有预设。
- **名字优先让用户取。** 用户说「你随便取」，就先向他提议一个名字再执行，不要自己闷头存。
- 建议名字里带上用途或单位，方便区分，例如「办公室周报（2026版）」「XX 大学学位论文（学院模板）」。
- 预设文件保存在用户自己的 `~/.local/share/doc-format/presets/`，带保存日期与来源说明。
- **提醒用户：** 预设保存的是排版参数与字体名；**换一台电脑后字体要重新确认一次**（本机字体只记在字体记忆里，不随预设走）。

## 载体能力矩阵

同一套排版意图，落到三种载体上能实现的不是一回事。**生成前必须把这个矩阵摆给用户看**，否则用户会以为「选一次规格，三种文件都一样」。

| 控制项 | DOCX | PDF | 公众号 HTML |
|---|---|---|---|
| 首行缩进 2 字符 | ✅ | ✅ | ✅（但惯例是不缩进） |
| 页边距 | ⚠️ 有设置但可被读者改动；双面印刷可用镜像内外侧 | ✅ 硬约束 | ⚠️ 只能设左右内边距 |
| 页码 / 页眉页脚 | ⚠️ 域，需更新 | ✅ 固定 | ❌ 无意义 |
| 页眉（单页章名 / 双页书名） | ✅ STYLEREF 域，随章自动变化 | ✅ | ❌ 无意义 |
| 绝对字号（pt） | ✅ | ✅ | ⚠️ 用 px，读者可缩放 |
| 字体 | ⚠️ 依赖读者机器 | ✅ 需内嵌 | ❌ 只能用系统字体栈 |
| 分页位置 | ⚠️ 软分页 | ✅ 硬分页 | ❌ 不可控 |
| 目录带页码 | ⚠️ 需更新域 | ✅ | ❌ 不支持 |
| 表格文字对齐 | ✅ | ✅ | ✅ |
| 图片 | ✅ | ✅ | ✅（用系统字体栈渲染） |
| 中英文自动间距 | ❌ 需手动处理 | ✅ | ⚠️ 靠手动加空格 |

公文版头（红头、发文字号、签发人、红色分隔线）、公文页码（单双页分开、左右一字线）、
公文版记（分隔线、抄送、印发机关/日期）与公文主体要素（主送机关顶格、署名与成文日期的 §7.3.5 定位）
目前**均可在 DOCX 生成**；书刊页眉（单页章名 / 双页书名）与内侧外侧镜像页边距也已生效。
公文主体要素由规格卡的 `body_elements` 段驱动，没声明这一段时一律按源稿原样排（不干预）。

一个共用开关要注意：**页眉和页码共用 `w:evenAndOddHeaders`**。任一方要求单双页不同，整篇都会打开它，另一方也必须写两套 —— 只写一套时，空着的那一侧会整片消失。

详细说明见 `references/carriers.md`。

## 字体策略

字体是这套流程里最容易出事的地方：标准要求某个字体，用户电脑上可能根本没有。**处置方式固定，没有「自动替换」这一说：**

```
规格要求的字体，本机有 → 直接用

本机没有 → 停下来问用户，二选一：
   A. 装上它
      ├─ 先查能不能免费、合法地拿到 → 能就给出官方下载地址与安装方法
      ├─ 用户装完 → 重新跑字体检测 → 确认认出来了 → 继续生成
      └─ 拿不到（商业字体）→ 只能走 B
   B. 换成本机已有的
      ├─ 跑 font_check.py --suggest <字体名> 拿到同类候选清单
      ├─ 用户在清单（或 font_check.py --list 的全部中文字体）里亲自指定一个
      └─ 写进规格卡对应槽位的 resolved 字段

两条都不选 → 中止生成，退出码 4，不产出半成品
```

**为什么禁止自动替换**：实测事故 —— LibreOffice 静默把中文替换成 `LinuxLibertine` / `DejaVuSans` / `FrankRuhlHofshi`，文件能打开、文本能提取，但字全错了，且没有任何提示。自动替换等于把错误藏起来。

核心事实：

- **开源可免费商用字体**（走路径 A 装，不是「替代」）：思源宋体、思源黑体、霞鹜文楷、朱雀仿宋（均为 SIL OFL 1.1）。**朱雀仿宋是少见的「仿宋 + 免费商用」组合**，公文场景值得优先考虑。
- **无免费渠道的商业字体**：仿宋_GB2312、方正小标宋简体、宋体 SimSun、黑体 SimHei、微软雅黑。
- **字体清单只在首次使用时全盘检测一次**，之后读 `~/.cache/doc-format/font-memory.json`，不要反复自检；
  用户中途装了字体用 `--remember` 记一笔。换一台电脑要重新首次检测。
- **公众号 HTML 是例外**：该载体只能用系统字体栈，属于载体限制，不算替身，但要在交付说明里写清。

```bash
python3 scripts/font_check.py --list                 # 本机有哪些中文字体（走字体记忆，不重扫）
python3 scripts/font_check.py --has "仿宋_GB2312"     # 某个字在不在
python3 scripts/font_check.py --remember 仿宋_GB2312  # 用户刚装好这个字体：记一笔，以后不再为它检测
python3 scripts/font_check.py --refresh              # 只有明确需要时才重新全盘检测
python3 scripts/font_check.py --guide 仿宋_GB2312     # 这个字体能不能免费拿到
python3 scripts/font_check.py --suggest 宋体          # 本机没有时，能改用哪些同类字体
python3 scripts/font_check.py --spec build/typography.spec.yaml   # 体检规格卡的字体是否齐全（缺则退出码 4）
python3 scripts/spec_check.py build/typography.spec.yaml          # 规格卡全面体检
```

完整策略、授权清单与核验日期见 `references/fonts.md`。

## 反模式

| 反模式 | 正确做法 |
|---|---|
| 把标题当成自己的决定：列出来就当用户同意了 | 标题是内容项：篇名给 2–3 个候选、小标题逐条列出并给替代写法，**等用户回过话**才算定稿；只听「可以」就回读一遍清单再确认 |
| 源稿没有标题层级（或只有一整段）就直接生成 | 先跑 `structure_check.py`（退出码 5＝未确认），**停下来**把统计与待确认清单给用户，逐条问过再生成；用户说「就是不要标题」才加 `--allow-flat` |
| 直接用 Markdown 生成，跳过错别字检查 | 先跑 `typo_check.py`，并逐条报告改动 |
| 直接用 Markdown 生成，跳过源文件体检 | 先跑 `md_normalize.py` |
| 一发现缺字体就自动挑一个近似的顶上 | 停下来问：装字体，还是从本机已有的里指定一个（写进 `resolved`） |
| 每次任务都重跑一遍全盘字体检测 | 首次检测一次写入字体记忆；之后读记忆，用户中途装的字体用 `--remember` 记一笔 |
| 照抄上一次任务里那台机器的字体清单 | 换一台电脑要重新首次检测 |
| 只报预设名字，不解释规格内容、不说核验日期 | 每条规格写清数值、含义与出处，并带时效声明 |
| 用户说标准变了，还继续沿用旧预设 | 要出处，或联网复查；确认后把结论写进用户数据目录那份记录，别改出厂文件 |
| 告诉用户「PDF 我可以帮你排一下」 | PDF 改不了字，如实说明并给出替代路径 |
| 一次甩 30 个问题给用户 | 分组问，每组 3-5 项，先给推荐值 |
| 把国标写死的值拿去问用户 | 标准规定的直接执行，只问标准没定的 |
| 对公众号 HTML 也要求页边距和页码 | 明确告知跳过，并写进报告 |
| 凭记忆引用国标编号或数值 | 查标准核验记录（出厂 + 你自己那份），无出处就标「惯例」 |
| 生成完就说「好了」 | 跑 `verify_output.py` 出报告，再渲染图片看一眼 |
| 渲染完的预览图留在用户目录里 | 看完立刻 `render_preview.py --clean --outdir preview/` 删掉；要再看就重新渲染 |
| 静默修改用户的稿子 | 先出体检报告，用户同意后再落盘 |
| 用户说「随便」就自己拍板 | 用预设默认值 + 差异项重新提问 |
| 用户一调用就套预设开始生成 | 先定三件事（要什么载体 / 骨架对不对 / 按哪套规格），定完再动手，中间不生成任何文件 |
| 只报内置预设，不翻用户自己存过的 | 开工先跑一次预设清单，把他存过的主动报给他 —— 不翻，这个 skill 就永远停在第一次用 |
| 第一问只摆预设、不提「我自己定」 | 预设是按体例分的，多数稿子不属于任何体例；第一问必须带上「我自己定」，并把可调的项连推荐值一起摆出来 |
| 任务做完就问「要不要存成预设」 | 只在用户改动过规格时才问；直接用内置预设、没改参数就不问 |
| 每次任务都重跑一遍全盘字体检测 | 首次检测一次即可，之后走字体记忆；用户中途装字体用 `--remember` 记一笔 |
| 结果不对就反复重排、反复试 | 先定位根因（规格写错 / 脚本 bug / 需求变了）；是 skill 的问题就停下告诉用户，别烧 token |
| 预设/schema/规格卡里登记了字段，就算「实现了」 | 登记 ≠ 生效。加字段时同时找**读取方**（生成脚本）与**校验方**（`verify_output` 要从成品里量出来）。历史上「签发人」「章从奇数页起」「表题位置」都是登记了没生效，报告还全绿 |
| 改了某个参数就再整篇生成一遍 | 只重新生成受影响的载体，并只修没通过的项 |
| 给用户加上他没要求的美化装饰 | 不做美化层，只做合规与载体适配 |
| 用户主动要美化装饰，含糊答应或硬去做 | 说清「擅长排得对、不擅长排得花」与「功能越多越易出错」，给替代路径，让他决定 |
| 跟用户汇报时甩脚本名、函数名、报错原文、退出码 | 说人话：这东西是干什么的、会怎样影响他手上那份文件。文件名只在括号里出现 |
| 一口气把发现的问题全倒给用户，不给推荐 | 一次只问一件事，选项不超过三个，每个写清代价，并明说推荐哪个 |
| 告诉用户「你自己看着办」 | 用户不懂技术，判断不了就该给推荐；他回「你定」再按推荐执行 |

## 高频疏漏项

以下问题多数人第一次排版不会想到，**在规格问询或校验阶段主动检查一遍**：

| 项 | 常见问题 | 怎么处理 |
|---|---|---|
| 公文要素缺项 | 用户给的稿子通常没有发文机关名称、发文字号、署名、成文日期 —— 这些是公文成立的要素，脚本不会替你编 | 缺一个就**中止生成**（`spec_check.py` 报错、`build_docx.py` 退出码 3），逐项问清再生成；用户只要练习稿/待补稿时，才用 `--allow-placeholders` 生成带〔占位符〕的版本，并明说不能当正式文件 |
| 图注与表注 | 图注应在图**下方**、表注在表**上方**（中文惯例），编号连续 | 在规格卡 `figures_tables` 里写清，校验时抽查编号连续性 |
| 块级元素的前后空 | 表格、图片、代码块、引用块、分隔线**没有首行缩进**，靠它们自己留空才不会与正文粘在一起；正文段间距为 0（中文靠缩进分段）时尤其明显 | 规格卡 `blocks` 段写 `space_before_lines` / `space_after_lines` / `caption_gap_lines`；不写脚本按 0.5/0.5/0.3 行给默认并打印说明（公文类应为 0，否则撑破 22 行/页） |
| 页眉放什么 | 有人要 logo、有人要章名、有人不要页眉 —— 这是内容不是格式，预设不能替他默认 | 先问用户，按 ①不放 ②章名 ③书名 ④机构名 ⑤图片 ⑥单双页各一样 报方向；写进 `header` 段（图片用 `image` + `image_height_mm`） |
| 图表编号与交叉引用 | 正文说「如图 3 所示」但图只有 2 张 | 全文核对编号，发现不一致要报告 |
| 目录与页码 | Word 目录是域，不更新就是不显示或页码错 | 交付时提醒用户按 F9 更新域 |
| 页眉页脚奇偶页 | 学位论文常要求奇偶页不同（单页章名、双页论文题目） | 在规格卡 `footer` 里明确，DOCX 需分节 |
| 脚注 / 尾注 | 有的要求脚注、有的要求尾注、有的要求文内注 | 先问清，转换时脚注容易丢，生成后要核对 |
| 公式 | Word 公式对象（OMML）转换后常变形 | 生成后渲染图片目视确认公式还在 |
| 图片分辨率 | 印刷需 300dpi，屏幕 150dpi 够 | 低于 200dpi 的图要提醒用户换源图 |
| 表格跨页 | 长表格跨页时表头应重复；行被切在页边界上会留下「有框线、无文字」的空行 | 表头重复由脚本自动写入；每行还会写入「禁止跨页断行」（`w:cantSplit`），这两项都不需要用户决定。生成后看跨页那一处 |
| 标题段间距 | 标题上下都紧贴文字，整页挤成一团；或另起页的章标题又被加了一段段前距，把内容往下推 | 在每级标题下写 `space_before_lines` / `space_after_lines`（或 `_pt`）。**不写时脚本会按「段前空一行、段后半行」补默认值并打印说明**；另起页的标题段前距应显式写 0 |
| 表格单元格对齐 | 同一列里有的行左对齐、有的行右对齐（逐格判断造成的），整列不齐 | **默认不干预**：源文件有 Markdown 对齐标记就用标记，用户明确要求才写 `header_alignment` / `text_column_alignment` / `number_column_alignment`，都没有就保持默认、不写任何对齐。若确要判定，必须**整列统一**，不许逐格判。表格**整体在页面上的位置**同样不预设（`table_alignment` 可显式要求 left/center/right）。生成后逐列看一眼 |
| 单位与数字 | 中文出版物用阿拉伯数字，单位用 GB 3100 系列 | 引用 `standards.md` 第五节的规则检查 |
| 标点挤压与避头尾 | 中文标点不能出现在行首（避头尾），Word 有「中文版式」开关 | 在交付说明里提醒，PDF 由排版引擎处理 |
| 装订线 | 装订侧需要额外留出装订线，否则字被夹住 | 规格卡 `binding` 字段，左右边距要不对称 |
| 批注与修订痕迹 | 别人的批注、修订记录会随文件一起发出去 | 交付前提醒用户接受/拒绝修订、删除批注 |
| 文档属性 | 作者名、公司名可能泄露隐私 | 提醒用户清理文件属性 |
| 无障碍 | HTML 图片需要 `alt` 文本 | 有图就补 alt，屏幕阅读器要用 |
| 字数与页数 | 有的场景有硬性字数/页数要求 | 生成后把字数页数报给用户 |

## 反空转纪律

这个 skill 最容易犯的错不是排错版，而是**在后台空转**：反复读全文、反复试错生成、反复追问，
最后 token 烧完了，交给用户一个垃圾。以下纪律用来防止这件事。

| 纪律 | 具体做法 |
|---|---|
| **模型不读全文** | 正文由脚本读。`typo_check.py` 出命中清单，模型只看命中的那几十行，不看十万字正文 |
| **能脚本做的都脚本做** | 抽取、结构识别、规范化、错别字、规格体检、生成、校验、渲图，全部是确定性脚本，零 token |
| **模型只做三件事** | 判体裁门槛、决定哪些拿不准的项要问、把这些问出口。其余不要插手 |
| **一次问完** | 确认单只发一条消息，四块一起给（我读到的 / 我识别到的 / 我拿不准的 / 我必须问的）。不许挤牙膏 |
| **生成只跑一轮** | 生成 → 校验 → 只修没通过的项。不要整篇重新生成，更不要「再试一次看看」 |
| **长稿抽样核对** | 一本书渲染成图片不可能全看，抽样正文页、章节首页、图表页、末页即可 |
| **拿不准先问再生成** | 不要先生成一版再问用户对不对。生成完再问，等于把前面的 token 全烧掉 |
| **不做用户没要求的事** | 包括美化、改写措辞、补充内容。见硬规则 11 |

## 出错处置纪律

生成结果不符合要求时，**默认动作不是「再来一遍」，而是「先定位」。**
反复重排有两个代价：烧掉大量 token，而且根因没修，下次照样犯。

**第一步：分清是哪一类问题。**

| 类别 | 判断依据 | 该怎么做 |
|---|---|---|
| 规格卡写错了 | 校验报告指出某项没落实，而规格卡里的值本身就不对 | 改规格卡，重新生成 |
| 用户需求变了 | 用户明确说要改成别的样子 | 改规格卡，重新生成 |
| **skill 本身有问题** | 规格卡没问题、脚本也没报错，但产出就是不对 —— **哪怕只错一小处也算** | **停下来，不要重排**，见下 |

**第二步：判断是 skill 的问题时，按这个顺序查。**

1. 先查问题清单 —— **两层都查**：出厂的 `references/known-issues.md` 与用户数据目录里那份。
   是不是已知问题？是就直接引用，不重复排查。
2. 再查校验报告里**哪一项**没通过，定位到具体脚本与具体函数，不要通读代码。
3. 用最小样例复现一次（一页文档、一个表格），确认根因，**不要靠推测**。

**第三步：告诉用户，让用户决定。**

说清三件事：**哪里不对、我判断根因是什么、建议怎么改**。然后等用户拍板。

**记的时机跟着决定走：** 先问他改不改。**他说改，修完就记进用户数据目录的 `known-issues.md`（写清现象与根因）；
他说不改，就不记** —— 他不认为那是问题，硬记下来只是噪音，清单越积越没人看。

但「不记」只针对**这条结论**：**每次出问题仍然要查一遍清单、仍然要当面告诉他**，
不能因为它不值得记就悄悄放过、更不能拖到第二次才说。

说的时候按「怎么跟用户说话」一节的模板来：**先一句话说结果，再说这件事对他手上这份文件的影响，
最后给两个选项、并明说推荐哪个。** 不要把脚本名、函数名、报错原文丢给用户，那等于让他自己翻译。
**说不出「选 A 会怎样、选 B 会怎样」，就说明我还没想清楚，先回去想。**

- 用户同意修 → 修完把结论记进用户数据目录的 `known-issues.md`（路径问 `scripts/user_data.py --path known-issues.md`），状态写「已修复」。
- 用户暂时不修 → 状态写「已知，暂不修」，继续把当前任务做完，并在交付说明里如实标注。

**禁止的做法：**

- 不改任何东西就重新生成一遍，看会不会碰巧变好；
- 换个说法再试一次、换个参数再试一次，用试错代替定位；
- 明明发现了 skill 的缺陷，却瞒着不说，硬着头皮交付。

## 怎么跟用户说话

用这套话术的用户，多数不写代码。你说得越专业，他越没法替你判断。
**他看不懂，就不会拍板；不会拍板，事情就卡在那儿 —— 最后只能由你替他猜，那就违背了「问清楚」这条命脉。**

### 三条骨架

**一、结论先行。** 第一句就把结果说完，不要铺垫背景、不要先讲过程。
他关心的是「我的文件到底行不行」，不是「我是怎么查出来的」。

**二、一段一件事。** 一句话一个意思，讲完就换段。把三件事塞进一段，读者会全部跳过。
需要列三点时，就用三个短段，别写成一大坨。

**三、一次只问一件事，选项不超过三个。** 每个选项都要写清**选它会怎样**（要花多少时间、
要不要动手、代价是什么）。给完选项，**再说一句我推荐哪个、为什么**。
用户说「你定」，就按推荐执行，不再追问。

### 说人话对照表

| 不要这样说 | 改成这样说 |
|---|---|
| `build_docx.py` 的 `HEADER_FIELD_TOKENS` 常量全项目零调用 | 程序里有两小段没人用的旧代码，删掉不影响任何功能 |
| 规格卡的 `page.size` 字段没有被读取 | 你选的 A4 纸，程序没照做 —— 你以为出的是 A4，实际出的是另一种大小 |
| 抛出 `FileNotFoundError` / 退出码 2 / traceback | 文件没找到，程序停下来告诉你了 |
| 校验报告：已落实 12 项、跳过 4 项 | 一共 16 条要求，12 条确认做到了，4 条这篇稿子用不上 |
| 需要改 `spec_lib.py` 与 `verify_output.py` 两个函数 | 要改两个地方，改完以后你自己存的预设就能直接用了 |
| `soffice` 不在 `PATH`，`--convert-to` 未找到可执行文件 | 这台电脑上缺一个叫 LibreOffice 的小工具，只有「出货成 PDF」这步要用它；Word 文件已经好了 |
| 走 AST 静态扫描 / 正则 / 解析器 / 依赖注入 | （不出现，说「我用程序自动查了一遍」就够） |

**必须提到文件时**，先说它是干什么的，再把文件名放括号里：
「你那份稿子的原始文件（`书稿.md`）不会被改动」。

### 让用户拍板时，照这个模板说

```
【出了什么事】一句话，不带术语。
【对你的影响】你手上这份文件会怎样 —— 字先看哪、表会不会跑偏、能不能直接拿去交。
【我建议】① 推荐：……，因为……  ② 另一种：……
【怎么回】直接回「1」或「2」就行。
```

模板里最关键的是**「我建议」那一行**。用户不懂技术，判断不了哪个方案更好；
你不给推荐，他就得靠猜，或者干脆说「你看着办」—— 那这句话就白问了。

### 自检

把要发的话念一遍，问自己三个问题：

- **一个不写代码的人，能听懂吗？** 有没有哪个词他需要查？
- **他知道该选哪个吗？** 有没有给推荐、有没有说清代价？
- **多久能看完？** 超过一屏就该拆、该删。

三条有一条不满足，就重写，不要发出去。

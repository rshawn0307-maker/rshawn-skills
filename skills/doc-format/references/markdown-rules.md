# Markdown 源文件规范化规则

上游脏，下游必乱。这一步在生成任何文件之前执行，由 `scripts/md_normalize.py` 完成。

**基本原则：只改格式，不改措辞。** 且必须先出报告，用户确认后才落盘。

## 一、必须修复的问题（按危害排序）

### 1. 硬换行切断自然段（危害最大）

Markdown 里一个自然段被写成多行：

```markdown
这是第一句话，写得很长很长，
于是作者手动换行了，
这实际上是同一个自然段。
```

生成 Word 后，**每一行都会首行缩进**，排版直接毁掉。必须合并为一段。

**判断规则：** 连续的普通文本行，若前一行结尾不是终止标点（`。！？：；"`）且后一行开头不是 Markdown 结构标记（`#` `-` `*` `>` `|` 数字加点），则判定为同一段，应合并。

**例外：** 两个空格结尾表示显式换行、代码块内、表格内、列表项内的换行不动。

### 2. 中英文之间缺少空格

```
错误：使用Python编写代码，效率提升30%
正确：使用 Python 编写代码，效率提升 30%
```

规则：**中文与英文/数字之间插入一个半角空格**。

不处理的例外：

- 中英文之间已有标点（`中文, English` 不加）
- 数字与单位符号之间（`30%`、`10kg` 不加）
- 专有名词内部（`GB/T 9704-2012` 不动）

### 3. 半角标点混用

| 错误 | 正确 | 说明 |
|---|---|---|
| `,` `.` `;` `:` `?` `!` | `，` `。` `；` `：` `？` `！` | 中文语境用全角 |
| `"..."` | `“...”` | 直引号改中文弯引号 |
| `'...'` | `‘...’` | 同上 |
| `--` 或 `-` | `——` | 破折号占两个字符位置 |
| `...` | `……` | 省略号六点，占两个字符位置 |
| `()` | `（）` | 中文语境用全角括号 |
| `《》` 内的 `《》` | `〈〉` | 书名号嵌套用单书名号 |

**判断依据：** 只在中文语境（前后字符为中文）时替换，代码块、行内代码、URL、英文段落里不动。

**一个例外：数字后面的半角句点不换。** 中文正文的句子结尾不会用半角点，所以「数字 + `.`」
几乎必然是**序号点**或**小数点**：`附件：1. 城市防汛隐患排查台账`、`1. 排查范围`、`3.14`。
照「中文语境」的通用规则把它们换成 `。`，会写出 `附件：1。城市防汛…`（实测过）——
附件号当场写错，而且公文附件说明要按「附件名首字」做回行对齐（GB/T 9704 §7.3.4），
前缀宽度也会跟着算错。规则见 `md_normalize.py` 的 `fullwidth_punct`。

### 4. 标题层级跳跃

```
错误： # 一级标题  →  ### 三级标题（跳过了 ##）
修复： 逐级递补，或提示用户确认层级关系
```

### 5. 表格问题

- 缺少分隔行（`|---|---|`）
- 各行竖线数量不一致（列数不齐）
- 对齐标记是可选项，缺了不算缺陷：本 skill 默认不干预对齐，**不要为了「好看」自动补标记**。
  只有用户明确要求对齐时才需要补：表头居中 `|:---:|`、数据左对齐 `|:---|`、数字右对齐 `|---:|`

**表格对齐标记会被 `build_docx.py` 直接翻译成单元格对齐方式**，是「表格文字居中」需求的落地手段。

### 6. 列表与正文之间缺少空行

Markdown 解析器对空行敏感，缺空行会导致列表被吞进上一段。

### 7. 引用块（`>`）的分段规则

**分段只看内容有没有分段，不看作者怎么写空行。** 下面两种写法，解析结果完全一致，无需人工整理，
规范化脚本也不要为了统一这两种写法去动源文件：

```markdown
> 第一段。
>
> 第二段。
```

```markdown
> 第一段。

> 第二段。
```

- 引用里的**列表项**（`> - 甲` / `> 1. 甲`）每一项自成一段，不会被并成一行；
- **引用套引用**（`> > 内层`）的多层 `>` 会被一并剥掉，`>` 不会原样印在纸上；
- 真正独立的两处引文（中间夹着正文）不会被合并 —— 合并只在「中间仅隔空行」时发生。

以上都由 `spec_lib.parse_markdown_blocks()` 与 `merge_adjacent_quotes()` 完成，规范化脚本不必处理。

## 二、绝对不能触碰的内容

以下区域原样保留，任何规范化都不得进入：

- 围栏代码块（` ``` ` 之间的全部内容）
- 行内代码（反引号包裹）
- 数学公式（`$...$`、`$$...$$`）
- 链接 URL 与图片路径
- HTML 标签与属性
- 参考文献条目（保持 `[1]` 这类编号原样）
- YAML front matter

## 三、标题的人工断行标记（`｜`）

长标题要回行时，断在哪儿是**内容判断**，不是格式判断：GB/T 9704-2012 §7.3.1 要求
「回行时，要做到词意完整，排列对称」，而脚本没有词典，只能按字数均衡猜 ——
实测把「城市防汛」切成了「城市防／汛」。

**写法**：在标题里用全角竖线 `｜`（半角 `|` 也认）标出断行位置，生成时按它断行：

```markdown
# 关于开展 2026 年度城市｜防汛隐患排查整治工作的通知
```

- 只对**标题行**有效；正文段落里出现 `｜` 不会被当成断行标记。
- 只标一处最常见（断成两行）；多标几处就按标的位置断成多行。
- **不写也照样能生成**：预设里声明了 `shape_rule`（如公文标题的「梯形或菱形」）时，
  脚本会自动挑一个「两行长短最均衡」的断点，并把断在哪儿打印出来。
  拿到输出后觉得断点不合适，再用 `｜` 标一次即可。

## 四、输出格式

脚本输出三部分：

1. **统计**：各类问题的数量
2. **明细**：每处问题所在行号、原文、建议修改
3. **修复文件**：`build/原文件名.normalized.md`（落在同级 build/ 子目录，不覆盖原文件、不堆在书稿目录里）

用户确认后，才决定是替换原文件还是保留两份。

## 五、检查清单

- [ ] 硬换行已合并，每个自然段是一行
- [ ] 中英文之间有半角空格
- [ ] 标点已全角化，引号已改为中文弯引号
- [ ] 破折号与省略号已规范化
- [ ] 标题层级无跳跃
- [ ] 长标题的断行位置合适（预设自动断的断点若不理想，用 `｜` 标出想要的断点）
- [ ] 表格有分隔行、列数一致、对齐标记正确
- [ ] 代码块、公式、URL 未被改动

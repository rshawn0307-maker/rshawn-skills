# 载体能力矩阵：DOCX / PDF / 公众号 HTML 各自能做什么

同一套排版意图，落到三种载体上能实现的程度完全不同。**生成前必须把这个矩阵讲给用户听**，否则用户会以为「选一次规格，三种文件长得一样」，交付时才发现公众号根本没有页码，DOCX 里设的页边距换个软件打开就跑。

图例：✅ 能落实 ｜ ⚠️ 有条件，需说明 ｜ ❌ 该载体无此概念，会跳过

## 一、总览

| 控制项 | DOCX | PDF | 公众号 HTML |
|---|---|---|---|
| 首行缩进 2 字符 | 原生段落属性 | 支持 | ⚠️ 技术可行，但屏幕惯例不缩进，用段间距 |
| 页边距 | 有页面设置，但读者可改、其他软件打开可能变 | 硬约束，所见即所得 | ❌ 无页概念；只能设左右内边距，上下由平台控制 |
| 页眉与页脚 | 域，需更新才显示 | 固定 | ❌ 无意义 |
| 页码 | 域；奇偶页不同需分节 | 固定，可奇偶页不同 | ❌ 无意义 |
| 绝对字号（pt） | 支持 | 支持 | ⚠️ 用 px，读者可在微信里缩放字号 |
| 字体 | 依赖读者机器是否装了 | 内嵌后跨机一致 | ❌ 只能用系统字体栈，无法指定具体字体 |
| 分页位置 | 软分页，内容增减会漂 | 硬分页，完全可控 | ❌ 完全不可控 |
| 章从奇数页开始 | 需手动分节插入空白页 | 可控 | ❌ 不可控 |
| 目录带页码 | 需更新域 | 生成即固定 | ❌ 不支持 |
| 表格文字对齐 | 支持 | 支持 | ✅ 内联样式可控制 |
| 表格三线表 | 需自定义边框 | 支持 | ⚠️ 内联边框可行，但编辑器可能重写表格样式，必须目视核对 |
| 中英文自动间距 | 需在源文本手动处理 | 支持 | ⚠️ 需在源文本手动加半角空格 |
| 标点挤压与避头尾 | Word 有「中文版式」选项，可开启 | 取决于排版引擎 | ❌ 不支持 |
| 图片分辨率 | 屏幕 150dpi 即可 | 印刷需 300dpi | ⚠️ 上传后被平台压缩，宽度建议 ≤ 1080px |
| 样式是否内联 | 不需要 | 不需要 | ✅ 必须内联，`class` 与 `<style>` 会被丢弃 |
| 文件可编辑性 | 强 | 基本不可编辑 | ⚠️ HTML 可改，粘进编辑器后需再核对一遍 |

**表格对齐的补充说明：**三种载体都能控制对齐，但**本 skill 不预设对齐风格**：
源文件写了 `:---` / `---:` / `:---:` 就照标记走，规格卡里显式声明了字段就照规格走，
两者都没有就完全不写对齐，保持 Word 与浏览器的默认。
手动指定时有一条配套规则：**按列判定、整列统一**，某列数据右对齐时该列表头也跟着右对齐，
避免同一列里有的行左对齐、有的行右对齐。

## 二、关键澄清话术

当规格要求的字体本机没有时：

> 我不会自动换一个「差不多的」字体。只有两条路：装上这个字体，或者你从本机已有的字体里指定一个。
> DOCX 与 PDF 是固定版式，缺字体就直接中止生成；公众号是流式载体，
> 字体由读者设备决定，属于载体本身的限制，不是替身。

当用户对 DOCX 要求精确控制分页时：

> DOCX 是软分页：只要内容改动或对方用不同版本的 Word 打开，分页就会漂。要精确控制分页，得用 PDF。

当用户要把文章发到公众号时：

> 公众号不是一个排版软件，而是一个会被平台改写样式的网页编辑器：字号只能用 px、字体只能用系统字体栈、正文里的外链会被去掉、样式必须写在每个标签上（内联）。所以「页边距、页码、指定宋体」这类要求在这个载体上做不到，我会明确标成跳过，而不是假装生效。
>
> 还有两种情况必须先跟用户确认，不要默认他知道：**正文带图片时**，图片会写进 HTML 的 `<img>`，但粘贴到编辑器后图片需要用户自己重新上传到公众号素材库；**带视频或 GIF 时**，视频无法通过粘贴 HTML 进入正文，只能在编辑器里手动插入，脚本只能留占位提示。

## 三、同一规格落到三种载体的翻译示例

意图层（用户选一次）：

```
正文：五号宋体（10.5pt）/ 行距固定值 15.6pt / 首行缩进 2 字符 / 西文 Times New Roman
一级标题：二号黑体（22pt）/ 居中 / 段前 24pt 段后 18pt / 另起页
表格：表题在上 / 无竖线（三线表）　←　对齐不预设，用户开口才按「表头居中 / 数据列左对齐」写
```

载体适配层（skill 自动翻译）：

| 意图 | DOCX | PDF | 公众号 HTML |
|---|---|---|---|
| 五号宋体 | `w:eastAsia="宋体"`，`w:sz=21`（半磅值）。本机没有「宋体」时先问用户：装字体，或指定本机已有的（写进 `resolved`），绝不自动换 | 内嵌规格卡里写的那个字体，10.5pt | ❌ 跳过，改用系统字体栈 |
| 行距 15.6pt | `w:spacing w:line="312" w:lineRule="exact"` | 同 DOCX | 改用倍数 `line-height: 1.75`（屏幕更松） |
| 首行缩进 2 字符 | `w:ind w:firstLineChars="200"` | 同 DOCX | 改成段间距 `margin-bottom: 1em` |
| 另起页 | `<w:br w:type="page"/>` | 硬分页 | 跳过，用空行或分隔符号区分 |
| 页边距 | `w:pgMar` | `w:pgMar` 且强制生效 | 只保留左右 `padding: 16px` |
| 三线表 | 自定义 `w:tblBorders`，只留顶、表头、底 | 同 DOCX | 内联 `border-top` 与 `border-bottom`，表头加下边框 |

## 四、生成顺序

```
Markdown（唯一真源）
   │
   ├── build_docx.py ──→ DOCX ──build_pdf.py──→ PDF
   │
   └── build_html.py ──→ 公众号 HTML（内联样式，供粘贴）
```

PDF 走 DOCX 中转而不是直接从 Markdown 渲染，原因是：

1. 本机没有 pandoc、LaTeX、WeasyPrint，但有 LibreOffice（已实测 `soffice` 可用），且效果可接受。
2. DOCX 的样式体系完整，转换时中文字体、缩进、表格边框都能带过去。
3. 转出来的 PDF 可以做二次校验（PyMuPDF 读字体与坐标）。

**这一跳有三个坑，前两个不处理 PDF 里的字会被静默替换**（详见 `references/fonts.md` 第七节）：

- 字体要装进 `<LibreOfficeDev>/Contents/Resources/fonts/truetype/`，装到上一级无效；
- DOCX 里若同时带 `w:eastAsiaTheme` 与 `w:eastAsia`，主题字体会压掉显式字体；
- **空白页会被默认丢掉。** 规格要求「章从奇数页起」时，上一章收在奇数页就会空出一页，
  而 LibreOffice 导出默认跳过空白页（`IsSkipEmptyPages` 默认 `true`），实测把 16 页的稿子导成 12 页。
  页数一变，后面每一页的左右（奇偶）整体错位 —— 看起来像「章从奇数页起没生效」，
  页码域却仍按 16 页计数，印出的页码与实际页序对不上。`build_pdf.py` 已显式关掉该选项。

所以生成 PDF 时必须带 `--spec`（`build_pdf.py` 会装齐规格要用的字体，装不齐就中止），
生成后必须跑 `verify_output.py --pdf`，它会**按规格逐个核对 PDF 里实际用的字体**。

三种载体都由同一个 Markdown 生成，**规格卡只写一份**：载体做不到的项登记在 `excluded`，
由各脚本自行跳过，并在合规报告里显式列出。

## 五、各载体校验方式

| 载体 | 校验方法 | 能查出什么 |
|---|---|---|
| DOCX | 解包读 `styles.xml`、`document.xml` | 字体、字号、行距、首行缩进、表格对齐是否真的写进去了 |
| PDF | PyMuPDF（`fitz`） | 字体是否内嵌、字体名、文字坐标（判断缩进与居中）、页数 |
| 公众号 HTML | `verify_output.py --html` 读源码 + 浏览器渲染目视 | 样式是否全部内联、有无 `class`、宽度上限、字号行高字色、外链是否按预设处理 |

三条校验通路本机依赖均已实测可用：`python-docx`、`PyMuPDF`、Python 标准库。

**HTML 要多做一步目视核对**：用浏览器打开 HTML 看一眼即可。微信客户端会二次改写样式，
源码校验通过不等于在手机里长得对。
